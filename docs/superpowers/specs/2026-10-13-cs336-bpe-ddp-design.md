# CS336 A1 BPE 增量更新与四卡训练设计

日期：2026-10-13  
状态：待用户审核；本文件记录已获准评估的设计，不代表实现已完成。

## 目标

1. 判断 BPE 合并阶段能否在保持原版合并顺序和词表结果的前提下进一步提速。
2. 量化更细粒度 pair 索引的峰值内存，并在运行完整 OWT 前设置可执行的内存安全门槛。
3. 将训练改为使用物理 GPU 4–7 的四卡 DDP，并验证数据准备与 GPU 计算重叠是否带来实际收益。

## 当前基线

- 原版保存在 original/；当前 cs336_basics/bpe.py 已用最大堆选择 pair，并通过 pair_to_word_ids 找到受影响词。
- 当前合并更新仍对每个受影响词生成新序列，并分别扫描旧、新序列构造 Counter。因此，它跳过了未受影响的词，但会在受影响词内重复扫描。
- 64 MiB OWT 前缀、vocab_size=1024 的历史测试中，当前版本 merge 阶段约 9.67 秒；增加预分词并行度只能把整个 BPE 用时从约 14.49 秒降到约 12.10 秒，说明合并更新仍有优化空间。
- 单卡合成训练测试中，batch=16 已接近吞吐饱和。四卡合成 DDP 测试：每卡 batch=16（全局 64）约 430,075 tokens/s、每卡峰值 4.08 GiB；每卡 batch=32（全局 128）约 449,386 tokens/s、每卡峰值 7.10 GiB。由于随机合成数据只让吞吐增加约 4.5%，默认采用每卡 16。
- 当前版峰值基线（随机前缀、vocab_size=1024，tracemalloc 关闭）：64 MiB 输入 14.60 秒、进程树峰值 0.327 GiB RSS / 0.316 GiB PSS；256 MiB 输入 41.95 秒、0.682 GiB RSS / 0.648 GiB PSS。两档均生成 767 次 merge 并正常退出。此数据用于候选对照，不足以单独证明完整 OWT 内存按线性扩展。
- 当前远端 cgroup memory.max 为 1,825,361,100,800 bytes，memory.current 约 13.7 GB；该值是运行时快照，不作为完整 OWT 的内存预测。预测需基于分级样本实测和峰值 RSS。

## BPE 方案与取舍

保留原版作为语义参照，比较以下候选：

1. 低内存局部增量候选：继续使用现有的“pair → word IDs”索引；只对受影响词做一次左到右处理，在合并时记录邻接 pair 的加减量，避免为旧序列和新序列各建 Counter。它不会建立每个 pair 的完整位置集合，内存增量较小。
2. 位置索引候选：以词内 token 位置为单位索引 pair 出现，合并后只更新合并位置及左右邻居。先在小样本上验证精确的左到右、非重叠合并语义，再测峰值 RSS；若索引的 Python 对象开销过大，则只保留紧凑数组实现作为候选，不默认采用 Python set/tuple 的全位置索引。
3. 当前版本：作为速度、内存和输出的回退基线。

所有候选均按词频加权 pair 计数。词频表压缩重复 pretoken；位置索引则额外记录 pair 出现在哪些位置，二者不是同一项优化。局部 pair 更新需正确处理重叠候选（例如 a a a 中两个重叠的 a-a）并保持参考实现的贪心左到右选择。

算法背景：已有 BPE 工作通过链接结构和 pair 出现位置索引来减少全序列重扫；本项目仍需以课程参考语义和本地测量决定实现是否值得采用。[论文](https://aclanthology.org/2023.findings-acl.38.pdf)

## 验证与准入门槛

### 正确性

- 对原版、当前版和每个候选使用相同输入，比较完整 merges 顺序及 vocab 字节内容，要求完全一致。
- 覆盖重复 pair、重叠 pair、频次并列的字节序 tie-break、special-token 边界、空/短输入。
- 对随机小词表多轮合并后，以全量重算 pair 计数作为 oracle，逐轮比较计数和索引。

### 性能与内存

- 在 64 MiB、256 MiB、必要时 512 MiB 的 OWT 前缀上，对照运行并至少重复三次；分别报告预分词、pair 选择、merge 更新、总时长和峰值 RSS。
- 内存测试默认关闭 tracemalloc，用 /usr/bin/time 的最大 RSS 与 cgroup memory.peak / memory.events 交叉检查。
- 位置索引只有在 merges/vocab 完全相等、没有异常/oom、256 MiB 样本中位总时长至少快 1.2 倍、峰值 RSS 不超过当前版的 1.5 倍，且按样本外推的 OWT 峰值低于运行时可用内存的 60% 时才考虑启用。
- 每次扩大输入前先实测较小档并外推内存；预测越过门槛即停止，不启动完整 OWT BPE。完整运行前再次检查同机内存压力和 cgroup OOM 计数。
- 比较 8、16、32 个预分词 worker 与合理 chunk 数，worker 加速须同时通过 RSS 门槛。不要因机器有很多 CPU 核就默认拉满 worker。
- 若位置索引不满足速度或内存门槛，优先保留低内存候选；若低内存候选也无稳定收益，则回退当前版，不以复杂度换取无实测收益。

## 四卡训练与数据流水线

- 使用 CUDA_VISIBLE_DEVICES=4,5,6,7 和 torchrun，每张可见 GPU 一个进程；物理卡 GPU 4–7 对应 local rank 0–3。
- 每卡 batch 默认 16，全局 batch 64；固定随机种子并按 rank 分片数据，记录 rank/world size。
- 只让 rank 0 写日志和 checkpoint。每 1,000 步验证、每 5,000 步保存一次，训练结束保存最终状态；保存使用单一滚动路径，不保留密集的中间 checkpoint。
- 先做合成 DDP smoke test，再用实际 tokenized OWT 小段验证读数、loss、保存和恢复。数据输入尝试 pinned memory、预取与 non-blocking 传输；只有真实输入端到端吞吐稳定改善时才保留额外数据加载复杂度。
- 若训练目录尚无 OWT token ID 数组，先单独完成 BPE/编码和空间检查，不在同一轮里启动正式长训练。
